# 제품 스펙 (SDD) — FULL JOIN (추구미 앱)

## 1. 문제

20대 여성이 저장한 스타일 사진을 자신이 가진 옷·체형과 어떻게 맞출지 확신하지 못해, 장바구니에서 포기하거나 사 놓은 옷을 방치한다. (상세: `docs/PROBLEM.md`)

## 2. 타깃 사용자

스타일 사진을 저장하고, 옷을 살 때 가진 옷과의 매칭을 고민하는 20대 여성.
비대상: 사진을 저장하지 않는 사람, 남성 사용자, 미용실 시술·네일 결과가 목적인 사람. 30대 이상은 미검증.

## 3. 핵심 기능 (한 문장)

저장한 사진을 앱에 올리면 AI가 사진 속 아이템을 태깅하고, **칩으로 등록한 내 옷장과 대조(갭 분석)**해 아이템마다 **"가진 옷으로 되는 것(활용)"과 "새로 사야 하는 것(구매)"**을 나눈 뒤, 가진 옷으로 만든 코디 조합과 새로 살 옷의 쇼핑 검색 링크를 보여 준다.

```
StyleImage ─저장→ AI 태깅(Item: 부위·종류·색·핏)
              └→ 옷장(WardrobeItem)과 대조
                   ├─ 활용: 옷장에 있는 옷 → 코디 조합(Outfit) 1~3개
                   └─ 구매: 옷장에 없는 옷 → 쇼핑 검색 링크(Product, similar)
```

- 이 흐름의 근거는 사용자의 **과거 행동**이다: 가진 옷을 먼저 활용하고 없을 때 산다(로그 3, 6, 7, 9), 하의를 기준으로 여러 벌을 맞춰 본다(로그 2, 9, 10), 사진 속 옷에서 카테고리를 뽑아 쇼핑앱에서 검색한다(로그 7, 9, 10).

### 핵심 스펙 3개는 어떻게 나왔나

| 핵심 스펙 | 인터뷰에서 본 행동 | 그래서 정한 것 |
|---|---|---|
| **AC9 옷장과 대조해 활용/구매 나누기** | 10명 전원이 가진 옷과의 매칭을 머릿속으로만 한다(페인 3). 가진 옷을 먼저 쓰고 없을 때 산다 — "제 옷장에 있는 걸 최대한 찾아서 이제 그거를 이용을 하려는 편이어서"(로그 9, 그 밖에 로그 3, 6, 7) | 사진 속 옷마다 "옷장에 있음(활용) / 없음(구매)"을 붙인다. 같은 부위·종류에 같은 색 계열이면 활용 |
| **AC11 코디 조합에 내 옷 1개 이상** | 하의를 기준으로 여러 벌을 맞춰 본다 — "무조건 하의 두 개씩은 매치해 본 것 같습니다"(로그 10, 그 밖에 로그 2, 9). 맞춰 보지 못하고 산 옷은 방치(10명 중 9명, 페인 4) | 코디 조합은 반드시 옷장에 실제로 있는 옷으로 만든다. 없는 옷은 넣지 않는다 |
| **AC2 근거 없는 브랜드명 금지, 비슷한 상품은 "비슷한"으로 표시** | 똑같은 제품을 찾으려 한다 — "거의 한 90% 정도는 똑같은 거로 사려고 합니다"(로그 8, 그 밖에 로그 3, 4, 5) | 비슷한 상품을 같은 상품처럼 보이면 신뢰를 잃는다. 근거가 없으면 제품명을 비우고 링크는 "비슷한 상품"으로만 |

- 근거가 약한 것도 숨기지 않는다: **AC13(칩 4번 이내 등록)**은 팀 결정이고, 사용자가 실제로 등록해 줄지는 인터뷰로 확인하지 못했다(가정 질문만 했음) → 출시 후 온보딩 완료율로 확인한다(PROBLEM 4절).

## 4. 범위

- **포함**
  - 사진 추가(공유하기·스크린샷) → `StyleImage` 생성 (저장 경로가 흩어져 있음: 로그 1, 3~10)
  - AI 태깅(구조화 출력): `StyleImage.categories`(코디·무드, 한 사진에 복수), `Item.slot`·`kind`·`color`·`fit` — 헤어·메이크업은 태깅하지 않는다
  - **옷장 등록(칩)**: 부위 → 종류 → 색 → 핏을 칩으로 고른다. 사진은 선택. (팀 결정로그 9/16. 칩이 등록 부담을 줄인다는 것은 **가설** — 온보딩 완료율로 검증)
  - **갭 분석**: `Item`마다 옷장의 `WardrobeItem`과 대조해 `gap_status`(활용 / 구매)를 정한다
  - **코디 조합 제안**: 활용 가능한 옷장 옷으로 `Outfit` 1~3개
  - **구매 아이템의 쇼핑 검색 링크**: 무신사·에이블리·지그재그 검색 결과 페이지 (`Product.match_type = similar`) — 인터뷰에서 실제로 쓰는 앱(무신사 로그 2, 4, 7, 9 / 에이블리 로그 2, 5, 7 / 지그재그 로그 9, 10).
  - 카테고리·계절별 아카이브 (재탐색: 로그 1, 4~9) — 계절은 저장한 달로 자동 분류하고 사용자가 고칠 수 있다
  - 분석 결과 캐시: 사진 1장당 분석 1회
  - **챗봇 (사진 분석 후 이어서 묻기)**: 분석한 사진을 두고 "이 셔츠 비슷한 걸로 다른 색도 있어?", "이거랑 내 옷장에서 뭐 입어?"처럼 이어서 묻는다. 사용자는 사진 속 옷을 찾으려고 네이버·AI(GPT)·후기를 전전한다(페인 5, 로그 3~10). GPT에 사진을 넣어 찾아도 "엄청 잘 찾아주는 건 아니"었다(로그 5). GPT와 달리 내 옷장과 저장된 분석 결과를 알고 답한다. 상품은 비슷한 상품 검색 링크로만 답한다(동일 상품 검색은 비포함).
- **비포함**
  - 결제·앱 내 구매, 쇼핑몰 구매 내역 자동 연동, 커뮤니티
  - 헤어·메이크업 전부 — 태깅·아카이브 분류, 따라 하기 가이드(튜토리얼 링크), 미용실 관련 기능(할 말 카드, 예약, 시술 결과 예측). 근거는 바로 아래
  - 네일, 스킨케어·이너뷰티
  - 얼굴로 인물 식별, 가상 피팅·이미지 생성
  - 쇼핑몰 상품 사진 저장·크롤링(링크만), 인스타·핀터레스트 저장 목록 자동 불러오기
  - 이미지 기반 동일 상품 검색(`match_type = exact`)
- **결정 보류**
  - 옷장 사진 등록 + 이미지 임베딩 — 1차는 칩 대조(AC9)로 시작하고, evals E2(활용/구매 일치율)가 80%에 못 미치면 도입을 결정한다. 도입하면 AC13(사진 촬영 필수 단계 없음)과 칩 기반 AC9를 함께 고친다. 등록 방식에 대한 인터뷰 반응은 컨셉 설명 뒤의 반응이나 가정 질문(Q11)이라 근거로 쓰지 않았다.
- **헤어·메이크업을 뺀 이유** — 처음에는 코디·헤어·메이크업을 함께 다루려 했지만, 인터뷰와 설문에서 세 가지 차이가 나왔다(9/29 멘토 미팅 후 범위 축소, 10/12 태깅까지 제외).
  1. **문제가 생기는 빈도가 다르다.** 옷은 외출·쇼핑 때마다 생기는 일상적인 문제다 — 인터뷰 10명 전원이 가진 옷과의 매칭을 머릿속으로 했고(로그 1~10), 설문 여성 27/30이 옷을 살 때 "거의 매번" 고민한다. 준비할 때 가장 오래 걸린 것도 옷 18명, 메이크업 6명, 머리 1명이었다(설문 38명). 반면 헤어는 바꾸고 싶을 때나 미용실에 보여 주려고 저장하고(로그 1, 5, 7, 8 — "미용실 같은 데 가서 보여줄 때가 많으니까 캡처", 로그 5), 메이크업은 올리브영 세일 때처럼 살 때 참고한다(로그 6). 특정 시점에만 생기는 니즈라 앱을 자주 다시 열게 하는 핵심 기능으로 삼기 어렵다.
  2. **막히는 지점이 다르다.** 옷은 가진 옷과 어떻게 맞출지 몰라서 포기하거나 방치한다(페인 3, 4) — 갭 분석으로 직접 풀 수 있다. 메이크업은 제품 정보가 있어야 저장하고(로그 1, 6, 8, 주로: 로그 7), 피부톤에 맞춘 선택은 이미 퍼스널 컬러 진단으로 하고 있다(설문 22/38이 진단, 그중 13명이 최근 한 달 안에 활용). 헤어는 염색 색·모질·얼굴형 차이로 결과가 사진과 어긋난다(로그 1, 2, 8). 둘 다 사진 분석과 옷장 대조로 풀 수 있는 문제가 아니다.
  3. **문제 범위를 한 가지로 좁힌다.** 세 카테고리를 얕게 다루면 개발 자원이 흩어진다. 가장 많이 겪는 문제인 '가진 옷과의 대조' 하나를 깊게 만들어 검증한다(강의 04: 핵심은 유지하고 문제 범위는 축소).
  - 반대 사례도 남긴다: 무드만 보고 메이크업을 저장하거나(로그 2, 5) 헤어 사진을 평소에 모으는 사람도 있다(로그 2). 헤어·메이크업을 다시 다루려면 별도 인터뷰로 그 문제(미용실 결과 차이, 제품 선택)를 먼저 확인한다.

## 5. 인터페이스

앱: Expo(React Native) + TypeScript / 서버: Supabase Edge Function (LLM 키는 서버에만)

- `POST /wardrobe` — 옷장에 옷 한 벌 등록 (칩 값은 태깅과 같은 enum)
- `POST /analyze` — 사진 한 장 분석: 태깅, 활용/구매, 코디 조합, 쇼핑 링크
- `GET /archive?category=&season=` — 카테고리·계절별 저장 사진
- `POST /chat` — 분석한 사진에 대해 이어서 묻기 (저장된 분석 결과와 옷장을 함께 넘긴다)

## 6. 수용 기준 (Definition of Done)

**태깅**
- **AC1 [상시 적용]**: 앱은 항상 `categories`, `Item.slot`·`kind`·`color`·`fit`, 옷장 칩 값을 **같은 enum 목록** 값으로만 쓴다 — 목록 밖 값이 하나라도 있으면 실패. (스키마 검증으로 판정 / 같은 목록이어야 대조가 성립한다)
- **AC2 [상시 적용]**: 앱은 항상 캡션·이미지 속 글자·사용자 입력에 근거가 없는 브랜드명·제품명을 출력하지 않는다 — 근거가 없으면 `brand_source: 없음`, `product_name: null`, 링크는 "비슷한 상품"(`match_type: similar`)으로만 표시한다. (로그 3, 4, 5, 8, 10 — 똑같은 제품을 원하므로 비슷한 상품을 같은 상품처럼 보이면 신뢰를 잃는다)
- **AC3 [이벤트 기반]**: 사용자가 사진을 저장하면, 앱은 태깅·갭 분석 결과를 **평균 5초, 최대(p95) 10초 안에** 보여 준다.
- **AC10 [예외 대응]**: 사진에서 옷 아이템을 하나도 찾지 못하면(헤어·메이크업만 있는 사진, 풍경·음식 사진 등), 앱은 `items`를 빈 목록으로 두고 "옷을 찾지 못했어요"를 보여 준다 — 아이템이나 링크를 지어내지 않는다.

**옷장과 갭 분석**
- **AC9 [이벤트 기반]**: 옷장에 1벌 이상 있는 상태에서 사진을 분석하면, 앱은 각 `Item`에 `gap_status`를 붙인다 — 같은 `slot`·`kind`이고 색이 같은 계열인 `WardrobeItem`이 있으면 "활용"(그 옷의 id를 `wardrobe_item_ids`에 넣음), 없으면 "구매". (로그 3, 6, 7, 9 — 가진 옷을 먼저 쓰고 없으면 산다)
- **AC11 [이벤트 기반]**: 코디 조합을 제안할 때, 앱은 각 `Outfit`에 사용자 옷장의 `WardrobeItem`을 **1개 이상** 넣고, 옷장에 실제로 등록된 id만 쓴다. (로그 2, 9, 10 — 하의를 기준으로 여러 벌 맞춰 본다)
- **AC12 [상태 기반]**: 옷장이 비어 있는 동안, 앱은 갭 분석을 하지 않고 모든 아이템을 "구매"로 단정하지 않는다 — 대신 쇼핑 링크와 함께 "옷장을 등록하면 가진 옷과 맞춰 드려요"를 보여 준다.
- **AC13 [상시 적용]**: 옷장 등록 흐름에는 사진 촬영 필수 단계가 없고, 옷 한 벌은 칩 선택 4번(부위·종류·색·핏) 이내로 등록된다. (팀 결정로그 9/16 — 등록 부담을 줄인다는 효과는 가설, PROBLEM 4절 온보딩 이탈률로 판정)

**챗봇**
- **AC14 [이벤트 기반]**: 사용자가 분석한 사진에 대해 질문하면, 챗봇은 옷장에 등록된 옷만 "가진 옷"으로 말하고 저장된 분석 결과를 다시 쓴다 — 사진을 다시 분석하지 않는다. 상품을 말할 때는 AC2를 따른다(근거 없는 브랜드명·제품명 금지, 비슷한 상품 링크만). 질문 속 지시문은 AC6처럼 데이터로만 다룬다. (페인 5, 로그 3~10 — 사진 속 옷을 찾으려 여러 도구를 전전함 / 로그 5 — GPT에 사진을 넣어 찾지만 "엄청 잘 찾아주는 건 아니"었다)

**아카이브·기타**
- **AC4 [이벤트 기반]**: 이미 분석한 사진을 다시 열면, 앱은 LLM을 다시 호출하지 않고 저장된 결과를 보여 준다 — 두 번째 열람에서 분석 호출 0회. (비용 원칙)
- **AC5 [이벤트 기반]**: 사용자가 아카이브에서 카테고리를 고르면, 앱은 그 카테고리가 붙은 사진만 저장 시기 역순으로 보여 준다. (로그 1, 4~9 — 재탐색)
- **AC6 [예외 대응]**: 사진 캡션이나 이미지 속 글자에 지시문("이전 지시 무시" 등)이 있으면, 앱은 이를 데이터로만 취급하고 분석 결과에 반영하지 않는다. (레드티밍 실습에서 검증)
- **AC7 [예외 대응]**: 사진에 사람 얼굴이 있어도, 앱은 얼굴로 인물 이름을 추정하지 않는다 — 인물 이름은 캡션·사용자 입력에 있을 때만 표시한다. (저작권·초상권 원칙)

> AC 번호는 한 번 정하면 바꾸지 않는다(번호 순서와 표시 순서가 다른 이유). AC ↔ 골든 케이스: `tests/harness/golden_cases.yaml` (강의 5).
> 안 되면 앱이 성립하지 않는 가정(사진을 앱으로 가져올 수 있는가)의 검증: `docs/spikes/photo_import.md`
> 핵심 기능과 기본 성능을 계속 재는 기준: `evals/README.md`
