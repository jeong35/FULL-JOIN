# 제품 스펙 (SDD) — FULL JOIN (추구미 앱)

## 1. 문제

20대 여성이 저장한 스타일 사진을 자신이 가진 옷과 어떻게 맞출지 확신하지 못해, 장바구니에서 포기하거나 사 놓은 옷을 방치한다. (상세: `docs/PROBLEM.md`)

## 2. 타깃 사용자

스타일 사진을 저장하고, 옷을 살 때 가진 옷과의 매칭을 고민하는 20대 여성.
비대상: 스타일 사진을 모아 두지 않는 사람, 남성 사용자, 미용실 시술·네일 결과가 목적인 사람. 30대 이상은 미검증.

## 3. 핵심 기능 (한 문장)

앱 피드(쇼핑몰·인플루언서 사진)에서 사용자가 마음에 드는 사진을 ♡하면, 업로드 때 미리 태깅해 둔 사진 속 아이템을 **칩으로 등록한 내 옷장과 대조(갭 분석)**한다. 같은 옷은 **활용**, 같은 종류의 비슷한 색 옷은 **비슷함**으로 알려 사용자가 활용할지 구매할지 선택하게 하고, 대응하는 옷이 없으면 **구매**로 안내한다. 최종 활용 아이템으로는 코디 조합을, 구매 아이템에는 쇼핑 검색 링크를 보여 준다.

```
피드 사진 ─업로드 시→ AI 태깅(Item: 부위·종류·색·핏) + 쇼핑몰 상품 정보
StyleImage ─♡→ 옷장(WardrobeItem)과 대조
                   ├─ 활용: 같은 옷 있음 → 코디 조합(Outfit) 1~3개
                   ├─ 비슷함: 비슷한 옷 있음 → 사용자가 활용 / 구매 선택
                   │                         ├─ 활용 → 코디 조합
                   │                         └─ 구매 → 쇼핑 검색 링크
                   └─ 구매: 대응하는 옷 없음 → 쇼핑 검색 링크(Product, similar)
```

- 이 흐름의 근거는 사용자의 **과거 행동**이다: 가진 옷을 먼저 활용하고 없을 때 산다(로그 3, 6, 7, 9), 하의를 기준으로 여러 벌을 맞춰 본다(로그 2, 9, 10), 사진 속 옷에서 카테고리를 뽑아 쇼핑앱에서 검색한다(로그 7, 9, 10).

### 핵심 스펙 3개는 어떻게 나왔나

| 핵심 스펙 | 인터뷰에서 본 행동 | 그래서 정한 것 |
|---|---|---|
| **AC9 옷장 대조 결과를 활용/비슷함/구매로 표시** | 10명 전원이 가진 옷과의 매칭을 머릿속으로만 한다(페인 3). 가진 옷을 먼저 쓰고 없을 때 산다 — "제 옷장에 있는 걸 최대한 찾아서 이제 그거를 이용을 하려는 편이어서"(로그 9, 그 밖에 로그 3, 6, 7) | 사진 속 옷마다 "같은 옷 있음(활용) / 비슷한 색만 있음(비슷함) / 없음(구매)"을 표시한다. `비슷함`은 최종 판정이 아니라 사용자가 활용 또는 구매를 선택하기 위한 정보다 |
| **AC11 코디 조합에 내 옷 1개 이상** | 하의를 기준으로 여러 벌을 맞춰 본다 — "무조건 하의 두 개씩은 매치해 본 것 같습니다"(로그 10, 그 밖에 로그 2, 9). 맞춰 보지 못하고 산 옷은 방치(10명 중 9명, 페인 4) | 코디 조합은 반드시 옷장에 실제로 있는 옷으로 만든다. 없는 옷은 넣지 않는다 |
| **AC2 근거 없는 브랜드명 금지, 비슷한 상품은 "비슷한"으로 표시** | 똑같은 제품을 찾으려 한다 — "거의 한 90% 정도는 똑같은 거로 사려고 합니다"(로그 8, 그 밖에 로그 3, 4, 5) | 비슷한 상품을 같은 상품처럼 보이면 신뢰를 잃는다. 근거가 없으면 제품명을 비우고 링크는 "비슷한 상품"으로만 |

- 근거가 약한 것도 숨기지 않는다: **AC13(칩 선택 4번 이내 등록)**은 팀 결정이고, 사용자가 실제로 등록해 줄지는 인터뷰로 확인하지 못했다(가정 질문만 했음) → 출시 후 온보딩 완료율로 확인한다(PROBLEM 4절). AI가 자동 추출하는 추가 특징은 사용자 선택 횟수에 포함하지 않는다.

## 4. 범위

- **포함**
  - **스타일 피드**: 앱이 쇼핑몰·인플루언서·연예인 사진(허락을 못 받으면 팀이 직접 찍은 사진)을 피드로 올리고, 사용자가 ♡하면 `StyleImage`로 저장된다. 사용자에게 사진을 받지는 않는다(10/12 팀 결정 — 사용자 사진 업로드는 나중 확장 후보). 인터뷰에서 사진이 인스타·캡처·DM·핀터레스트에 흩어져 있던 것(로그 1, 3~10)은 "앱 안 한곳에 모은다"는 근거
  - **피드 구성**: 사용자가 스타일 필터를 직접 누르면 그 스타일 사진만 보여 준다. 홈 피드는 온보딩에서 고른 취향 70% + 이웃 스타일 20% + 무작위 10%로 섞는다 — 취향은 바뀌고(로그 7, 8, 10) 새 스타일 시도가 해결 가설이므로(PROBLEM 4절) 고른 취향만 보여 주지 않는다. 이웃 스타일(10/13 팀 결정): 캐주얼→스트릿·스포티 / 미니멀→시크·청순 / 러블리→청순·프레피 / 청순→러블리·미니멀 / 엘레강스→미니멀·글램 / 시크→미니멀·글램 / 스트릿→캐주얼·스포티 / 레트로→캐주얼·프레피 / 프레피→러블리·레트로 / 스포티→캐주얼·스트릿 / 글램→시크·엘레강스. ♡ 반응으로 비율을 바꾸는 것은 나중 확장
  - **쇼핑몰 상품 정보 저장**: 피드에 올리는 쇼핑몰 사진은 상품명·브랜드·상품 링크를 함께 저장해, 사진 속 옷이 무엇인지 안다(허락받은 쇼핑몰만)
  - AI 태깅(구조화 출력, 피드에 올릴 때 1회): `StyleImage.style`(스타일 키워드 0~2개 — 피드에 올릴 때 팀이 확정, 모델은 추천), `Item.slot`·`kind`·`color`·`visual_fit` — 헤어·메이크업은 태깅하지 않는다
  - **옷장 등록(칩)**: 부위 → 종류 → 색 → 핏을 칩으로 고른다. 사진은 선택. (팀 결정로그 9/16. 칩이 등록 부담을 줄인다는 것은 **가설** — 온보딩 완료율로 검증)
  - **갭 분석**: `Item`마다 옷장의 `WardrobeItem`과 대조해 `gap_status`(활용 / 비슷함 / 구매)를 정한다
  - **코디 조합 제안**: 활용 가능한 옷장 옷으로 `Outfit` 1~3개
  - **구매 아이템의 쇼핑 검색 링크**: 무신사·에이블리·지그재그 검색 결과 페이지 (`Product.match_type = similar`) — 인터뷰에서 실제로 쓰는 앱(무신사 로그 2, 4, 7, 9 / 에이블리 로그 2, 5, 7 / 지그재그 로그 9, 10).
  - 스타일·계절별 아카이브 (재탐색: 로그 1, 4~9) — 계절은 저장한 달로 자동 분류하고 사용자가 고칠 수 있다
  - 분석 결과 캐시: 사진 1장당 분석 1회
  - **챗봇 (사진 분석 후 이어서 묻기)**: 분석한 사진을 두고 "이 셔츠 비슷한 걸로 다른 색도 있어?", "이거랑 내 옷장에서 뭐 입어?"처럼 이어서 묻는다. 사용자는 사진 속 옷을 찾으려고 네이버·AI(GPT)·후기를 전전한다(페인 5, 로그 3~10). GPT에 사진을 넣어 찾아도 "엄청 잘 찾아주는 건 아니"었다(로그 5). GPT와 달리 내 옷장과 저장된 분석 결과를 알고 답한다. 상품은 비슷한 상품 검색 링크로만 답한다(동일 상품 검색은 비포함).
- **비포함**
  - 결제·앱 내 구매, 쇼핑몰 구매 내역 자동 연동, 커뮤니티
  - 헤어·메이크업 전부 — 태깅·아카이브 분류, 따라 하기 가이드(튜토리얼 링크), 미용실 관련 기능(할 말 카드, 예약, 시술 결과 예측). 근거는 바로 아래
  - 네일, 스킨케어·이너뷰티
  - 체형 분석·체형별 추천 (10/13 팀 결정 — 특정 체형을 기준으로 삼지 않는다)
  - 얼굴로 인물 식별, 가상 피팅·이미지 생성
  - 허락 없는 쇼핑몰·인스타 사진 크롤링, 인스타·핀터레스트 저장 목록 자동 불러오기
  - 사용자 사진 업로드(공유하기·캡처) — 나중 확장 후보
  - 이미지 기반 동일 상품 검색(`match_type = exact`)
- **결정 보류**
  - 옷장 사진 등록 + 이미지 임베딩 — 1차는 칩 대조(AC9)로 시작하고, evals E2(활용/비슷함/구매 일치율)가 80%에 못 미치면 도입을 결정한다. 도입하면 AC13(사진 촬영 필수 단계 없음)과 칩 기반 AC9를 함께 고친다. 등록 방식에 대한 인터뷰 반응은 컨셉 설명 뒤의 반응이나 가정 질문(Q11)이라 근거로 쓰지 않았다.
- **헤어·메이크업을 뺀 이유** — 처음에는 코디·헤어·메이크업을 함께 다루려 했지만, 인터뷰와 설문에서 세 가지 차이가 나왔다(9/29 멘토 미팅 후 범위 축소, 10/12 태깅까지 제외).
  1. **문제가 생기는 빈도가 다르다.** 옷은 외출·쇼핑 때마다 생기는 일상적인 문제다 — 인터뷰 10명 전원이 가진 옷과의 매칭을 머릿속으로 했고(로그 1~10), 설문 여성 27/30이 옷을 살 때 "거의 매번" 고민한다. 준비할 때 가장 오래 걸린 것도 옷 18명, 메이크업 6명, 머리 1명이었다(설문 38명). 반면 헤어는 바꾸고 싶을 때나 미용실에 보여 주려고 저장하고(로그 1, 5, 7, 8 — "미용실 같은 데 가서 보여줄 때가 많으니까 캡처", 로그 5), 메이크업은 올리브영 세일 때처럼 살 때 참고한다(로그 6). 특정 시점에만 생기는 니즈라 앱을 자주 다시 열게 하는 핵심 기능으로 삼기 어렵다.
  2. **막히는 지점이 다르다.** 옷은 가진 옷과 어떻게 맞출지 몰라서 포기하거나 방치한다(페인 3, 4) — 갭 분석으로 직접 풀 수 있다. 메이크업은 제품 정보가 있어야 저장하고(로그 1, 6, 8, 주로: 로그 7), 피부톤에 맞춘 선택은 이미 퍼스널 컬러 진단으로 하고 있다(설문 22/38이 진단, 그중 13명이 최근 한 달 안에 활용). 헤어는 염색 색·모질·얼굴형 차이로 결과가 사진과 어긋난다(로그 1, 2, 8). 둘 다 사진 분석과 옷장 대조로 풀 수 있는 문제가 아니다.
  3. **문제 범위를 한 가지로 좁힌다.** 세 카테고리를 얕게 다루면 개발 자원이 흩어진다. 가장 많이 겪는 문제인 '가진 옷과의 대조' 하나를 깊게 만들어 검증한다(강의 04: 핵심은 유지하고 문제 범위는 축소).
  - 반대 사례도 남긴다: 무드만 보고 메이크업을 저장하거나(로그 2, 5) 헤어 사진을 평소에 모으는 사람도 있다(로그 2). 헤어·메이크업을 다시 다루려면 별도 인터뷰로 그 문제(미용실 결과 차이, 제품 선택)를 먼저 확인한다.

## 5. 인터페이스

앱: Expo(React Native) + TypeScript / 서버: Supabase Edge Function (LLM 키는 서버에만)

- `POST /wardrobe` — 옷장에 옷 한 벌 등록. `photo_url`은 선택이며 칩 값은 태깅과 같은 enum을 쓴다.
  - 입력: `{user_id, slot, kind, color, visual_fit, photo_url?}`
  - 출력: `{wardrobe_item: {id, user_id, slot, kind, color, visual_fit, photo_url?}}`
- `POST /analyze` — 운영자가 피드에 올릴 사진을 한 번 태깅한다. 사용자가 ♡할 때 다시 호출하지 않는다. 모델 출력 형식은 `src/fulljoin/schemas/style_image.schema.json`, 프롬프트는 `src/fulljoin/prompts/parse_query.md`다.
  - 입력: `{style_image_id, image_url, source, caption?, shopping_product?: {brand, product_name, url}}`
  - 출력: `{style_image_id, style[], items: [{item_id, slot, kind, color, visual_fit, visibility, brand, product_name, brand_source}]}`
- `GET /feed?style=` — 홈 피드 또는 선택한 스타일 피드를 가져온다. `style`을 생략하면 AC15의 14·4·2 구성을 적용한다.
  - 출력: `{style_images: [{id, thumbnail_url, style[], source}]}`
- `POST /style-images/{style_image_id}/heart` — 저장된 태깅 결과를 사용자 옷장과 대조하고 아카이브에 저장한다.
  - 입력: `{user_id}`
  - 출력: `{style_image_id, saved_at, items: [{item_id, gap_status, wardrobe_item_ids[], decision_options[]}], outfits: [{outfit_id, wardrobe_item_ids[], item_ids[]}], products: [{item_id, platform, url, match_type}]}`
  - `gap_status: "비슷함"`이면 `decision_options: ["활용", "구매"]`를 주며 앱이 둘 중 하나로 자동 단정하지 않는다. `활용` 또는 `구매`이면 `decision_options`는 빈 목록이다.
- `POST /style-images/{style_image_id}/items/{item_id}/decision` — `비슷함`인 아이템에 대해 사용자가 최종 활용/구매를 정한다.
  - 입력: `{user_id, decision: "활용" | "구매"}`
  - 출력: `{item_id, decision, outfits: [{outfit_id, wardrobe_item_ids[], item_ids[]}], products: [{item_id, platform, url, match_type}]}`
- `GET /archive?style=&season=` — 스타일·계절별로 ♡한 사진을 가져온다.
  - 출력: `{style_images: [{id, thumbnail_url, style[], season, saved_at}]}`
- `POST /chat` — 저장된 분석 결과와 옷장을 재사용해 이어서 답한다.
  - 입력: `{user_id, style_image_id, message}`
  - 출력: `{answer, analysis_id_used, claimed_owned_item_ids[], products: [{item_id, platform, url, match_type}]}`

## 6. 수용 기준 (Definition of Done)

**태깅**
- **AC1 [상시 적용]**: 앱은 항상 `style`, `Item.slot`·`kind`·`color`·`visual_fit`, 옷장 칩 값을 **같은 enum 목록** 값으로만 쓴다 — 목록 밖 값이 하나라도 있으면 실패. (스키마 검증으로 판정 / 같은 목록이어야 대조가 성립한다 / 목록: `src/fulljoin/schemas/style_image.schema.json`)
- **AC2 [상시 적용]**: 앱은 항상 캡션·이미지 속 글자·저장된 쇼핑몰 상품 정보(`brand_source: 쇼핑몰_상품정보`)·사용자 입력에 근거가 없는 브랜드명·제품명을 출력하지 않는다 — 근거가 없으면 `brand_source: 없음`, `product_name: null`, 링크는 "비슷한 상품"(`match_type: similar`)으로만 표시한다. (로그 3, 4, 5, 8, 10 — 똑같은 제품을 원하므로 비슷한 상품을 같은 상품처럼 보이면 신뢰를 잃는다)
- **AC3 [이벤트 기반]**: 사용자가 피드 사진을 ♡하면, 앱은 갭 분석 결과를(태깅은 업로드 때 끝나 있다) **평균 5초 이내, p95 10초 이내**에 보여 준다.
- **AC10 [예외 대응]**: 피드에 올리려는 사진에서 옷 아이템을 하나도 찾지 못하면(헤어·메이크업만 있는 사진, 풍경·음식 사진 등), 앱은 `items`를 빈 목록으로 두고 그 사진을 피드에 올리지 않는다(업로드 화면에 "옷을 찾지 못했어요" 표시) — 아이템이나 링크를 지어내지 않는다.

**옷장과 갭 분석**
- **AC9 [이벤트 기반]**: 옷장에 1벌 이상 있는 상태에서 사용자가 사진을 ♡하면, 앱은 각 `Item`에 `gap_status`를 붙인다 — 같은 `slot`·`kind`(카디건·후드집업·베스트·점프수트는 두 부위에 다 속하므로 `kind`만 비교. 종류가 다르면 비슷해 보여도 다른 옷 — 셔츠와 블라우스는 다르다)이고 **같은 색**인 `WardrobeItem`이 있으면 "활용", 같은 색은 없고 **같은 계열 색**만 있으면 "비슷함"(두 경우 모두 그 옷의 id를 `wardrobe_item_ids`에 넣음), 둘 다 없으면 "구매". `비슷함`은 최종 활용/구매 판정이 아니라 사용자에게 선택을 요청하는 정보 상태이며, 앱은 두 선택지를 모두 보여 준다. 색 계열: 화이트·아이보리 / 베이지·브라운 / 블랙·차콜·그레이 / 네이비·블루·스카이블루 / 연청·중청 / 진청·흑청 / 그린·카키·민트 / 레드·와인·핑크 / 퍼플·라벤더 / 옐로우·오렌지 / 실버·골드 (색이 null(판단 불가)·기타(목록 밖)·멀티면 계열 판정을 하지 않고, 같은 부위·종류의 옷이 옷장에 있으면 "비슷함"). (로그 3, 6, 7, 9 — 가진 옷을 먼저 쓰고 없으면 산다 / 로그 9 "완전 똑같은 옷 아니어도" — 비슷한 것도 쓴다. 같은 색과 비슷한 색을 구분해 보여 주는 것은 AC2와 같은 원칙: 비슷한 것을 같은 것처럼 보이지 않는다)
- **AC11 [이벤트 기반]**: 코디 조합을 제안할 때, 앱은 각 `Outfit`에 사용자 옷장의 `WardrobeItem`을 **1개 이상** 넣고, 옷장에 실제로 등록된 id만 쓴다. (로그 2, 9, 10 — 하의를 기준으로 여러 벌 맞춰 본다)
- **AC12 [상태 기반]**: 옷장이 비어 있는 동안, 앱은 갭 분석을 하지 않고 모든 아이템을 "구매"로 단정하지 않는다 — 대신 쇼핑 링크와 함께 "옷장을 등록하면 가진 옷과 맞춰 드려요"를 보여 준다.
- **AC13 [상시 적용]**: 옷장 등록 흐름에는 사진 촬영 필수 단계가 없고, 옷 한 벌은 `slot`·`kind`·`color`·`visual_fit`을 정하는 칩 선택 **4회 이내**로 등록된다. AI가 사진에서 자동 추출하는 추가 특징은 사용자 선택 횟수에 포함하지 않는다. (팀 결정로그 9/16 — 등록 부담을 줄인다는 효과는 가설, PROBLEM 4절 온보딩 이탈률로 판정)

**챗봇**
- **AC14 [이벤트 기반]**: 사용자가 분석한 사진에 대해 질문하면, 챗봇은 옷장에 등록된 옷만 "가진 옷"으로 말하고 저장된 분석 결과를 다시 쓴다 — 사진을 다시 분석하지 않는다. 상품을 말할 때는 AC2를 따른다(근거 없는 브랜드명·제품명 금지, 비슷한 상품 링크만). 질문 속 지시문은 AC6처럼 데이터로만 다룬다. (페인 5, 로그 3~10 — 사진 속 옷을 찾으려 여러 도구를 전전함 / 로그 5 — GPT에 사진을 넣어 찾지만 "엄청 잘 찾아주는 건 아니"었다)

**아카이브·기타**
- **AC4 [이벤트 기반]**: 피드 사진은 업로드 때 한 번만 태깅하고, 사용자가 ♡하거나 다시 열 때 앱은 LLM 태깅을 다시 호출하지 않는다 — 사진당 태깅 호출 1회(사용자 수와 무관). (비용 원칙)
- **AC5 [이벤트 기반]**: 사용자가 아카이브(♡한 사진)에서 스타일을 고르면, 앱은 그 스타일이 붙은 사진만 ♡한 시기 역순으로 보여 준다. (로그 1, 4~9 — 재탐색)
- **AC15 [이벤트 기반]**: 사용자가 홈 피드를 열면, 앱은 사진 20장 중 온보딩에서 고른 취향 스타일 14장, 이웃 스타일 4장, 그 밖의 스타일 2장을 보여 준다(70/20/10). 사용자가 스타일 필터를 고르면 그 스타일이 붙은 사진만 보여 준다. (로그 7, 8, 10 — 취향이 바뀐다 / 10/13 팀 결정)
- **AC6 [예외 대응]**: 피드 사진의 캡션·쇼핑몰 상품 설명·이미지 속 글자에 지시문("이전 지시 무시" 등)이 있으면, 앱은 이를 데이터로만 취급하고 분석 결과에 반영하지 않는다. (레드티밍 실습에서 검증)
- **AC7 [예외 대응]**: 사진에 사람 얼굴이 있어도, 앱은 얼굴로 인물 이름을 추정하지 않는다 — 인물 이름은 캡션·사용자 입력에 있을 때만 표시한다. (저작권·초상권 원칙)

> AC 번호는 한 번 정하면 바꾸지 않는다(번호 순서와 표시 순서가 다른 이유). 모든 AC는 판정 가능한 골든 케이스와 연결한다(강의 5). AC9의 매칭 구현 판정 케이스는 `tests/harness/golden_cases.yaml`, 나머지 제품 계약과 AC9의 사용자 선택 의미는 `tests/harness/product_golden_cases.yaml`에 있다. `tests/test_acceptance_contracts_golden.ts`는 SPEC의 AC가 하나라도 케이스와 연결되지 않으면 실패하고, 각 계약 케이스의 정상 예시는 통과하며 결함 예시는 거부되는지 확인한다. 아직 구현되지 않은 기능의 계약 케이스는 구현 완료를 뜻하지 않으며, 기능 구현 시 같은 판정기를 실제 출력에 연결해야 한다.
> 안 되면 앱이 성립하지 않는 가정(구조화 출력)의 검증: `docs/spikes/structured_output.md`
