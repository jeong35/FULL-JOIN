# 제품 스펙 (SDD) — FULL JOIN (추구미 앱)

> 강의 4 산출물 2. **무엇을** 만드는가의 단일 진실 공급원.
> 선행 산출물: `docs/PROBLEM.md`, `docs/ontology.yaml`. 용어는 온톨로지 대표어를 쓴다.
>
> ⚠️ **초안.** 수용 기준(AC)은 이후 골든 케이스와 evals의 판정 기준이므로 팀이 직접 확정한다. `[팀 확정]` 표시가 결정할 자리다.

## 1. 문제

20대 여성이 저장한 스타일 사진을 자신이 가진 옷·체형과 어떻게 맞출지 확신하지 못해, 장바구니에서 포기하거나 사 놓은 옷을 방치한다. (상세: `docs/PROBLEM.md`)

## 2. 타깃 사용자

스타일 사진을 저장하고, 옷을 살 때 가진 옷과의 매칭을 고민하는 20대 여성.
비대상: 사진을 저장하지 않는 사람, 남성 사용자, 미용실 시술·네일 결과가 목적인 사람. 30대 이상은 미검증.

## 3. 핵심 기능 (한 문장)

저장한 사진에 ♡를 누르면 AI가 사진 속 아이템을 태깅하고, **칩으로 등록한 내 옷장과 대조(갭 분석)**해 아이템마다 **"가진 옷으로 되는 것(활용)"과 "새로 사야 하는 것(구매)"**을 나눈 뒤, 가진 옷으로 만든 코디 조합과 새로 살 옷의 쇼핑 검색 링크를 보여 준다.

```
StyleImage ─♡→ AI 태깅(Item: 부위·종류·색·핏)
              └→ 옷장(WardrobeItem)과 대조
                   ├─ 활용: 옷장에 있는 옷 → 코디 조합(Outfit) 1~3개
                   └─ 구매: 옷장에 없는 옷 → 쇼핑 검색 링크(Product, similar)
```

- 이 흐름의 근거는 사용자의 **과거 행동**이다: 가진 옷을 먼저 활용하고 없을 때 산다(로그 3, 6, 7, 9), 하의를 기준으로 여러 벌을 맞춰 본다(로그 2, 9, 10), 사진 속 옷에서 카테고리를 뽑아 쇼핑앱에서 검색한다(로그 7, 9, 10).

## 4. 범위

- **포함**
  - 사진 추가(공유하기·스크린샷)와 ♡ 저장 → `StyleImage` 생성 (저장 경로가 흩어져 있음: 로그 1, 3~10)
  - AI 태깅(구조화 출력): `StyleImage.categories`(한 사진에 복수), `Item.slot`·`kind`·`color`·`fit`
  - **옷장 등록(칩)**: 부위 → 종류 → 색 → 핏을 칩으로 고른다. 사진은 선택. (팀 결정로그 9/16. 칩이 등록 부담을 줄인다는 것은 **가설** — 온보딩 완료율로 검증)
  - **갭 분석**: `Item`마다 옷장의 `WardrobeItem`과 대조해 `gap_status`(활용 / 구매)를 정한다
  - **코디 조합 제안**: 활용 가능한 옷장 옷으로 `Outfit` 1~3개
  - **구매 아이템의 쇼핑 검색 링크**: 무신사·에이블리·지그재그 검색 결과 페이지 (`Product.match_type = similar`) — 인터뷰에서 실제로 쓰는 앱(무신사 로그 2, 4, 7, 9 / 에이블리 로그 2, 5, 7 / 지그재그 로그 9, 10). 결정로그의 '무신사·29CM'은 인터뷰 언급이 없어 `[팀 확정]`
  - 카테고리·계절별 아카이브 (재탐색: 로그 1, 4~9) — 계절 기준은 열린 질문(제안: 저장 월 자동 + 사용자 수정)
  - 분석 결과 캐시: 사진 1장당 분석 1회
- **비포함**
  - 결제·앱 내 구매, 쇼핑몰 구매 내역 자동 연동, 커뮤니티
  - 미용실 예약·시술 결과 예측, 네일, 스킨케어·이너뷰티
  - 얼굴로 인물 식별, 가상 피팅·이미지 생성
  - 쇼핑몰 상품 사진 저장·크롤링(링크만), 인스타·핀터레스트 저장 목록 자동 불러오기
  - 이미지 기반 동일 상품 검색(`match_type = exact`)
- **결정 필요** `[팀 확정]`
  - **자연어 입력(챗봇)** — 인터뷰 근거가 없다. 2차로 미루거나, 저장된 태그를 재사용하는 보조 기능으로 가설 표시
  - **옷장 사진 등록 + 임베딩** — 칩만으로 대조하면 임베딩을 쓸 수 없다. 스파이크의 "태깅만 vs 태깅+임베딩" 비교로 사진을 받을 가치가 있는지 정한다 (`docs/spikes/wardrobe_matching.md`)
  - **헤어·메이크업 따라 하기 가이드** — 근거 1건(로그 6). 얕게 둘지 범위 밖으로 둘지

- **팀 기획 화면별 인터뷰 근거** (팀 노션 "화면·기능" 목록 기준) — 근거가 없는 기능은 MVP에서 빼거나 '가설'로 표시한다 (발견 게이트 감점 사유 ① "증거 없는 주장") `[팀 확정]`

  | 화면·기능 | 인터뷰 근거 | 제안 |
  |---|---|---|
  | 사진 정보창 (♡ → 태깅 + 갭 분석 + 코디·링크) | 페인 3·4·5 (로그 1~10) | 포함 (핵심 기능) |
  | 내 옷장 (칩 등록) | 매칭 고민 10명 전원(페인 3). 칩 방식 자체는 가설 | 포함 |
  | 마이 아카이브 (카테고리·계절별) | 페인 2 (로그 1, 4~9) | 포함 |
  | 사진 추가 (공유하기·스크린샷) | 저장 경로가 흩어짐 (로그 1, 3~10) | 포함 |
  | 미용실 할 말 카드 | 미용실 결과가 사진과 다름 (로그 1, 2, 7, 8) — 카드가 해결책이라는 근거는 없음 | 가설로 표시 |
  | 돋보기 피드 (팀 시드 룩) | 없음 — 인터뷰는 사용자가 **이미 저장한 사진**을 다뤘다 | 가설 또는 2차 |
  | 온보딩 취향 입력 | 없음 | 옷장 등록으로 대체 또는 최소화 |
  | 챗봇 (날씨 코디·색상 바꿔 찾기) | Q10 요청(로그 2, 5 — 희망은 증거 아님), 날씨 앱으로 미리 코디를 계획한 과거 행동 1건(로그 2) | 가설로 표시 |

## 5. 인터페이스 (계획 — 미구현)

앱: Expo(React Native) + TypeScript / 서버: Supabase Edge Function (LLM 키는 서버에만) `[팀 확정: 스택]`

- `POST /wardrobe` — 입력 `{slot, kind, color, fit, photo_id?}` (칩 값은 태깅과 **같은 enum**) → 출력 `{wardrobe_item_id}`
- `POST /analyze` — 입력 `{image_id}` → 출력
  ```
  {image_id, categories[],
   items: [{item_id, slot, kind, color, fit,
            gap_status: "활용" | "구매",
            wardrobe_item_ids[],          # 활용일 때 대조된 옷장 옷
            links: [{platform, url, match_type}],   # 구매일 때
            product_name, brand_source}],  # brand_source: 캡션 / 이미지_속_텍스트 / 사용자_입력 / 없음
   outfits: [{outfit_id, members: [{slot, wardrobe_item_id | null, item_id}]}]}
  ```
- `GET /archive?category=&season=` — 출력 `{images: [{image_id, thumbnail, categories[], saved_at}]}`
- `GET /health` — `{status: "ok"}`

> `gap_status`·`wardrobe_item_ids[]`·`outfits[]`가 응답에 있다는 것 자체가 "내 옷장 기준으로 판단한다"를 구조로 강제한다. 칩 값과 태깅 값이 같은 enum을 쓰기 때문에 대조가 가능하다.

## 6. 수용 기준 (Definition of Done)

EARS 문형 "[조건]일 때, 앱은 [동작]한다". 조건 유형을 [ ]에 표시하고 근거 로그를 함께 적는다.

**태깅**
- **AC1 [상시 적용]**: 앱은 항상 `categories`, `Item.slot`·`kind`·`color`·`fit`, 옷장 칩 값을 **같은 enum 목록** 값으로만 쓴다 — 목록 밖 값이 하나라도 있으면 실패. (스키마 검증으로 판정 / 같은 목록이어야 대조가 성립한다)
- **AC2 [상시 적용]**: 앱은 항상 캡션·이미지 속 글자·사용자 입력에 근거가 없는 브랜드명·제품명을 출력하지 않는다 — 근거가 없으면 `brand_source: 없음`, `product_name: null`, 링크는 "비슷한 상품"(`match_type: similar`)으로만 표시한다. (로그 3, 4, 5, 8, 10 — 똑같은 제품을 원하므로 비슷한 상품을 같은 상품처럼 보이면 신뢰를 잃는다)
- **AC3 [이벤트 기반]**: 사용자가 사진에 ♡를 누르면, 앱은 태깅·갭 분석 결과를 **평균 5초, 최대(p95) 10초 안에** 보여 준다. `[팀 확정: 시간]`
- **AC10 [예외 대응]**: 사진에서 옷·헤어·메이크업 아이템을 하나도 찾지 못하면(풍경·음식 사진 등), 앱은 `items`를 빈 목록으로 두고 "아이템을 찾지 못했어요"를 보여 준다 — 아이템이나 링크를 지어내지 않는다.

**옷장과 갭 분석**
- **AC9 [이벤트 기반]**: 옷장에 1벌 이상 있는 상태에서 사진을 분석하면, 앱은 각 `Item`에 `gap_status`를 붙인다 — 같은 `slot`·`kind`이고 색이 같은 계열인 `WardrobeItem`이 있으면 "활용"(그 옷의 id를 `wardrobe_item_ids`에 넣음), 없으면 "구매". (로그 3, 6, 7, 9 — 가진 옷을 먼저 쓰고 없으면 산다) `[팀 확정: 색 계열 규칙]`
- **AC11 [이벤트 기반]**: 코디 조합을 제안할 때, 앱은 각 `Outfit`에 사용자 옷장의 `WardrobeItem`을 **1개 이상** 넣고, 옷장에 실제로 등록된 id만 쓴다. (로그 2, 9, 10 — 하의를 기준으로 여러 벌 맞춰 본다)
- **AC12 [상태 기반]**: 옷장이 비어 있는 동안, 앱은 갭 분석을 하지 않고 모든 아이템을 "구매"로 단정하지 않는다 — 대신 쇼핑 링크와 함께 "옷장을 등록하면 가진 옷과 맞춰 드려요"를 보여 준다.
- **AC13 [상시 적용]**: 옷장 등록 흐름에는 사진 촬영 필수 단계가 없고, 옷 한 벌은 칩 선택 4번(부위·종류·색·핏) 이내로 등록된다. (팀 결정로그 9/16 — 등록 부담을 줄인다는 효과는 가설, PROBLEM 4절 온보딩 이탈률로 판정)

**아카이브·기타**
- **AC4 [이벤트 기반]**: 이미 분석한 사진을 다시 열면, 앱은 LLM을 다시 호출하지 않고 저장된 결과를 보여 준다 — 두 번째 열람에서 분석 호출 0회. (비용 원칙)
- **AC5 [이벤트 기반]**: 사용자가 아카이브에서 카테고리를 고르면, 앱은 그 카테고리가 붙은 사진만 저장 시기 역순으로 보여 준다. (로그 1, 4~9 — 재탐색)
- **AC6 [예외 대응]**: 사진 캡션이나 이미지 속 글자에 지시문("이전 지시 무시" 등)이 있으면, 앱은 이를 데이터로만 취급하고 분석 결과에 반영하지 않는다. (레드티밍 실습에서 검증)
- **AC7 [예외 대응]**: 사진에 사람 얼굴이 있어도, 앱은 얼굴로 인물 이름을 추정하지 않는다 — 인물 이름은 캡션·사용자 입력에 있을 때만 표시한다. (저작권·초상권 원칙)
- **AC8 [이벤트 기반]**: `GET /health` 요청이 오면 200과 `{"status":"ok"}`를 반환한다. (미구현)

> AC 번호는 한 번 정하면 바꾸지 않는다(번호 순서와 표시 순서가 다른 이유). AC ↔ 골든 케이스: `tests/harness/golden_cases.yaml` (강의 5).
