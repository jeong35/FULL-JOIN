# 코디 유사도 비교 v1

> 배포 단계와 인증 기준은 `PRIVATE_BETA_POLICY.md`를 따른다. 매칭 알고리즘과 Golden Case는 변경하지 않는다.

## 적용 범위

기존 `AC9`의 `활용`·`비슷함`·`구매` 판정은 유지한다. 코사인 유사도는 같은 판정 버킷 안의 옷장 후보와 `AC11` 대체 후보를 정렬하고, 하트 응답에 한 줄 근거 `match_metadata`를 더하는 데 사용한다. 따라서 기존 모바일 응답 필드는 바뀌지 않는다. 사용자 응답에 유사도 숫자를 공개하지 않는다.

## 특성 벡터와 가중치

| 특성 | 가중치 |
|---|---:|
| 종류 | 0.35 |
| 색 | 0.25 |
| 핏 | 0.15 |
| 소재 | 0.10 |
| 무늬 | 0.07 |
| 상세 | 0.05 |
| 계절 | 0.03 |

범주형 값은 one-hot, 배열 값은 multi-hot으로 만든다. 색 블록은 정확 색 0.7과 기존 AC9 색 계열 0.3의 multi-hot으로 표현한다. 각 특성 블록을 먼저 정규화한 후 가중치의 제곱근을 곱해 합친다. 두 옷에서 모두 알려진 특성만 비교하며, 공통 특성이 2개 미만이거나 공통 가중치 합이 0.5 미만이면 점수를 내지 않는다. 누락 값과 알 수 없는 enum, 비교 근거가 아닌 색 `멀티`·`기타`는 일치로 보지 않는다.

초기 임계값은 `활용 0.90`, `비슷함 0.70`이다. 현재 API 판정을 바꾸는 값이 아니라 `matchOutfitItems`의 실험용 분류값이며, 사람 승인 골든을 추가하기 전까지 가설로 취급한다.

## 결정성과 안전 규칙

- 슬롯이 다르면 후보에서 제외한다. 카디건·후드집업·베스트·점프수트의 기존 교차 슬롯만 허용한다.
- 기본 후보는 같은 종류로 제한하여 `AC9`를 보존한다.
- 동점은 `wardrobe_item_id` 오름차순이다.
- 코디 전체 매칭은 같은 옷장 ID를 두 자리에 중복 배정하지 않는다.
- API는 요청 `user_id`로 조회한 옷장만 `classifyGap`에 전달하고, metadata는 해당 AC9 결과의 `wardrobe_item_ids[0]`만 참조한다. 따라서 같은 종류라도 실제 색 버킷 밖 후보가 metadata로 새지 않는다. 다만 MVP는 인증 없이 요청의 `user_id`를 신뢰하므로 악의적인 타 사용자 ID 대입 방지는 후속 인증 과제다.

## 하트 응답 추가 필드

각 `items[]`에 아래 필드가 추가된다. 기존 필드는 그대로 유지된다.

```json
{
  "match_metadata": {
    "wardrobe_item_id": "WARDROBE-1",
    "reason_code": "fit_difference",
    "reason": "같은 종류와 색의 블랙 일자 슬랙스가 있어요. 사진은 와이드, 내 옷은 일자라 실루엣이 달라질 수 있어요."
  }
}
```

후보가 없는 `구매`에서는 `wardrobe_item_id`가 `null`이고 `reason_code`는 `no_candidate`다. 내부 similarity는 재현 확률이 아니며 API/UI에 노출하지 않는다.

## 기존 규칙과 비교

| 사례 | 기존 판정 | v1 적용 |
|---|---|---|
| 같은 종류·같은 색·같은 핏 | 활용 | 활용 유지, 동일 후보 중 최고 점수 |
| 같은 종류·같은 색·다른 핏 | 활용 | 활용 유지, 핏이 더 가까운 후보 우선 |
| 같은 종류·같은 계열 색 | 비슷함 | 비슷함 유지, 색·핏 점수로 후보 정렬 |
| 다른 종류 | 구매 | 구매 유지, 승인된 대체 종류 안에서만 코사인 정렬 |
| 슬롯 불일치 | 구매 | 후보 제외 |
| 빈 옷장·정보 부족 | 기존 빈 결과 | 후보 없음 또는 결정적 fallback, 점수 비공개 |
