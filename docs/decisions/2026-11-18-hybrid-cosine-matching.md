# 옷장 비교 알고리즘 결정 — 규칙 기반 후보 + 코사인 순위(A안)

- 작성일: 2026-11-18
- 상태: A안 로컬 통합·검증 완료, main/운영 미반영
- 작업 브랜치: `codex/stabilize-cosine-chat` (`origin/main@b53b6d6` 기준)
- 관련 AC: AC1, AC9, AC11, AC13

## 1. 결정 요약

현재 MVP에서는 **기존 스키마와 규칙으로 비교 가능한 후보 및 판정 상태를 먼저 결정하고, 코사인 유사도는 그 후보 안에서 순위를 정하는 데 사용한다.** 이를 A안으로 부른다.

코사인 유사도만으로 `활용`·`비슷함`·`대체`·`구매`를 모두 결정하지 않는다. 현재 데이터와 라벨이 충분하지 않고, 종류 one-hot만으로는 서로 다른 종류가 실제로 대체 가능한 관계인지 알 수 없기 때문이다.

향후 사람 라벨과 사용자 선택 데이터가 충분히 쌓이면 **슬롯 필터 + 종류 관계 점수 + 속성 코사인** 구조인 B안을 shadow mode로 검증한 뒤 전환 여부를 결정한다.

## 2. 상태의 의미

서버의 정식 `gap_status`는 기존 계약대로 다음 세 가지다.

- `활용`: 같은 종류이며 같은 색인 옷이 있음
- `비슷함`: 같은 종류이며 같은 색 계열인 옷이 있음. 사용자가 활용 또는 구매를 선택함
- `구매`: 위 조건을 만족하는 옷이 없음

`대체`는 별도의 `gap_status`가 아니다. `구매` 아이템에 대해 코디 생성 단계에서 승인된 대체 종류의 옷을 찾았을 때 화면에 표시하는 상태다. 대체 옷이 있어도 원래 아이템의 `gap_status`는 `구매`로 유지한다.

## 3. 현재 A안 처리 순서

### 3.1 공통 안전 조건

다음 조건은 유사도 점수보다 우선한다.

1. 현재 사용자의 옷장에 실제로 등록된 옷만 후보로 사용한다.
2. 슬롯이 호환되지 않으면 후보에서 제외한다.
3. 카디건·후드집업·베스트·점프수트의 기존 교차 슬롯 규칙만 허용한다.
4. 누락 값과 알 수 없는 enum은 일치로 취급하지 않는다.
5. 색 `멀티`·`기타`는 색 일치 근거로 사용하지 않는다.
6. 한 코디에 같은 옷장 아이템을 두 번 넣지 않는다.
7. 동점은 `wardrobe_item_id` 오름차순으로 결정한다.

### 3.2 같은 종류 비교

기존 AC9 규칙으로 판정 버킷을 먼저 만든다.

1. 같은 종류·같은 색 후보 → `활용` 버킷
2. 같은 종류·같은 색 계열 후보 → `비슷함` 버킷
3. 후보가 여러 개면 버킷 안에서 코사인 유사도 내림차순으로 정렬

따라서 핏이나 소재가 다르더라도 기존 `gap_status` 의미는 바뀌지 않는다. 코사인은 더 적합한 옷을 먼저 보여 주는 역할만 한다.

### 3.3 대체 비교

`구매` 아이템은 기존 대체 종류표로 후보 종류를 먼저 제한한다.

1. 승인된 대체 종류인지 확인
2. 같은 색 후보를 우선
3. 다음으로 같은 색 계열 후보
4. 각 색 버킷 안에서 코사인 유사도로 순위 결정

코사인이 임의로 새로운 대체 관계를 만들지는 않는다.

## 4. 현재 유사도 특성

범주형 특성은 one-hot, 복수 값은 multi-hot으로 표현한다. 각 특성 블록을 L2 정규화한 뒤 가중치의 제곱근을 적용한다. 두 아이템에서 공통으로 알려진 특성만 계산한다.

| 특성 | 초기 가중치 |
|---|---:|
| 종류 | 0.35 |
| 색 | 0.25 |
| 핏 | 0.15 |
| 소재 | 0.10 |
| 무늬 | 0.07 |
| 상세 | 0.05 |
| 계절 | 0.03 |

- 최소 공통 특성: 2개
- 최소 공통 가중치: 0.50
- 실험용 `활용` 임계값: 0.90
- 실험용 `비슷함` 임계값: 0.70

이 임계값은 현재 AC9 판정을 변경하지 않는다. 독립 매칭 실험과 향후 B안 검증을 위한 초기 가설이다. 유사도 0.8을 재현 확률 80%로 해석하지 않는다.

## 5. A안을 선택한 이유

- 기존 MVP의 AC9·AC11 의미와 프론트 응답 계약을 유지할 수 있다.
- 잘못된 `활용` 또는 `대체` 판정이 사용자 신뢰에 미치는 위험을 줄인다.
- 데이터가 적은 초기에도 결정론적으로 동작한다.
- 현재 수동 대체 종류표의 팀 결정을 보존한다.
- 코사인 결과를 별도 내부 평가에 사용할 수 있다. 사용자 피드백 수집과 운영 저장은 동의 정책 합의 전 구현하지 않는다.

## 6. 향후 B안

B안은 다음 구조를 목표로 한다.

1. 슬롯은 강한 필터로 유지
2. 종류 관계를 `같은 종류 / 대체 가능 / 관련 종류 / 비교 불가`로 모델링
3. 색·핏·소재·무늬·상세·계절의 코사인 유사도를 계산
4. 종류 관계 점수와 속성 유사도로 `활용 / 비슷함 / 대체 / 구매`를 판정

종류 관계를 학습하거나 확장하려면 종류 one-hot뿐 아니라 다음 특성이 필요하다.

- 티셔츠류·니트류·재킷류·코트류 등의 종류 그룹
- 착용 역할과 레이어 위치
- 길이와 실루엣
- 계절과 소재
- 사람이 승인한 대체 가능 관계

B안은 운영 결과를 바로 바꾸지 않고 A안과 동시에 계산하는 shadow mode로 먼저 평가한다.

## 7. 학습 데이터 수집 방향

초기에는 팀이 비교 쌍을 직접 라벨링한다. 이후 사용자가 동의한 경우 선택 결과를 품질 개선 데이터로 사용할 수 있다.

권장 사용자 피드백:

- `잘 맞아요`
- `애매해요`
- `안 맞아요`
- `적합한 옷이 없어요`
- 선택 이유: 종류 / 색 / 핏 / 소재 / 계절
- 여러 후보 중 실제로 선택한 옷

함께 저장할 정보:

- 비교 당시 사진 아이템 특성
- 노출한 옷장 후보와 순서
- 후보별 점수
- 알고리즘·가중치 버전
- 사용자의 선택

사용자 안내 문구 예시:

> 선택한 결과를 옷 비교 추천의 정확도를 개선하는 데 사용해도 될까요? 옷 정보와 선택 결과만 사용하며, 언제든 참여를 중단할 수 있어요.

초기에는 선택 즉시 모델을 바꾸는 온라인 학습을 사용하지 않는다. 오입력·편향·악의적 입력을 검토할 수 있도록 오프라인 배치 학습과 버전별 평가·롤백을 사용한다.

## 8. 비교 실험

| 실험안 | 방식 | 예상 역할 |
|---|---|---|
| A | 기존 규칙 + 판정 버킷 내부 코사인 | 현재 운영 후보, 초기 정확도와 안정성 우선 |
| B | 슬롯 필터 + 종류 관계 + 속성 코사인 | 데이터 축적 후 가장 높은 정확도 후보 |
| C | 슬롯만 필터 + 전체 코사인 | 대체 발견률 비교용, 초기 운영에는 사용하지 않음 |

평가 지표:

- `활용` 오판율
- `대체` 오판율
- 정답 후보 Top-1·Top-3 포함률
- 옷이 있는데 `구매`로 판정한 비율
- 옷이 없는데 `활용`·`대체`로 판정한 비율
- 사용자 선택 전환율과 `안 맞아요` 비율

## 9. 추가 결정 필요

1. `match_metadata.reason`을 사용자 화면에 표시할지 진단용으로만 유지할지

3. 가중치·임계값 검증을 위한 사람 라벨 규모와 분리 방식
4. 사용자 피드백 수집 동의 문구와 보관 정책
5. B안 전환을 검토할 최소 데이터량과 합격 지표
