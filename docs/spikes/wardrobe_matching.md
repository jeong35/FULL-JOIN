# 스파이크 — 사진 태깅과 칩 옷장 대조(갭 분석)

> 강의 4 산출물 4. 목적은 완성이 아니라 학습이다. 남기는 것은 **판단**이다.
>
> ⚠️ **실험 전 계획 단계.** 1~4절은 실험 전에 팀이 확정하고(`[팀 확정]`), 5~6절은 실험 후 실측값으로 채운다. 결과를 보고 3절의 합격선이나 판정 규칙을 바꾸지 않는다.

## 1. 가장 위험한 가정

**"멀티모달 LLM이 일상 캡처 사진에서 의류의 핵심 속성(부위·종류·색·핏)을 정해진 형식(JSON)으로 정확히 추출하고, 이를 칩으로 등록한 내 옷장과 대조해 '가진 옷으로 되는 것(활용) / 새로 사야 하는 것(구매)'을 사람이 판단하는 것과 비슷하게 나눌 수 있다."**

- 실패 영향: 제품의 핵심 기능(SPEC 3절 갭 분석)이 이 가정 위에 서 있다. 인터뷰 10명 모두 가진 옷과의 매칭을 머릿속으로만 하고 있었고(페인 3 — 로그 1~10), 9명이 맞춰 보지 못한 채 산 옷을 방치했다(페인 4). 대조가 틀리면 "가진 옷인데 사라고 하거나, 없는 옷을 있다고 하는" 앱이 되어, 머릿속 매칭보다 못해진다.
- 근거 부족: 강의 3 실습은 텍스트 파싱이었다. 인스타 캡처·핀터레스트 사진(잘림, 필터, 여러 사람)에서 아이템별 속성을 뽑는 품질, 그리고 그 결과가 사람이 칩으로 고른 값과 맞는지는 확인한 적이 없다.
- 대체 비용: 사용자가 사진 속 아이템을 직접 태그하게 하면 대체할 수 있지만, 그러면 "♡ 한 번으로 판단"이라는 가치가 사라진다.
- 다른 후보와 비교:
  - 쇼핑몰에서 비슷한 상품 찾기: 에이블리·지그재그·무신사가 이미 이미지 검색을 제공한다. 우리가 못 해도 대체 수단이 있다 → 제품의 존재 이유를 흔들지 않는다.
  - 칩 등록이 온보딩 이탈을 줄이는가: 제품이 나온 뒤 사용 관찰로만 판정할 수 있다(PROBLEM 4절) → 지금 실험할 수 없다.
  - 그래서 **태깅·대조가 틀리면 제품 정체성이 무너지고, 대체 수단도 없다** — 1순위.

## 2. 시간 제한

- 기간: 3일 타임박스. 데이터 준비(옷장 칩 등록, 평가용 사진 선정)는 1일 안에 끝낸다.
- API 예산: 평가 사진 30장 × 3회 실행 규모(약 90회 호출).
- 종료 조건: 3일 경과 또는 30건 평가 완료 중 먼저 오는 시점. 종료 시 결과와 무관하게 멈추고 그 시점까지의 결과로 판정한다.

## 4. 방법

**0. 데이터 준비 (우리 데이터)**
- 옷장: 은재·정인이 각자 옷 25벌을 **칩으로** 등록한다(부위·종류·색·핏) → `WardrobeItem` 50개. 상의·하의·아우터가 고르게 섞이게 한다. 비교 실험을 위해 옷 사진도 한 장씩 찍어 둔다(로컬 보관).
- 평가용 사진: 팀 시드 룩과 두 사람이 저장해 둔 코디 사진 중 전신이 보이는 30장. **프롬프트·태그 목록을 만들거나 고치는 데 쓰지 않은 사진**으로 고른다. 원본은 저장소에 올리지 않는다(저작권).
- 태그 목록(enum): `src/fulljoin/schemas/item.schema.json` — 칩 목록과 같은 파일을 쓴다(SPEC AC1).

**1. 정답 만들기**
- ① 속성 라벨: 30장의 주 아이템을 두 사람이 서로 보지 않고 각자 라벨한 뒤, 다른 것은 함께 보고 합의한다. 합의 전 불일치 건수를 기록한다(사람 사이의 차이이지 모델 오류가 아니다).
- ② 갭 판단: 질의마다 옷장 주인이 "내 옷장에 이걸로 쓸 옷이 있나? 있으면 어느 옷?"을 고른다. 다른 팀원이 따로 판단해 비교하고 합의한다.

**2. 모델 출력 만들기**
- 모델: Anthropic API(비전 + 구조화 출력) ____ / 프롬프트: `src/fulljoin/prompts/` ____ / temperature 0 / 사진마다 3회 실행(③ 파싱 성공률 측정용, ①②는 1회차 결과로 판정). 실험 중 모델·프롬프트·설정을 바꾸지 않는다.
- 대조: SPEC AC9의 규칙(같은 부위·종류, 같은 색 계열이면 "활용")을 코드로 적용한다. 동점은 옷 id 오름차순.
- **추가 비교 (선택, 채택 판정에는 쓰지 않음)**: 옷 사진이 있는 경우 "태그 대조 + 이미지 임베딩(예: Marqo-FashionSigLIP) 유사도"로 ②를 다시 계산해, 태그만 쓸 때보다 일치율이 오르는지 본다. → 옷장 등록에 사진을 받을 가치가 있는지의 근거(SPEC 4절 결정 필요)

**3. 대조**
- 3절 규칙으로 ①~④를 센다.

이 단계 밖의 일(앱 화면, 프롬프트 최적화, 코드 정리)은 하지 않는다.

## 6. 판단과 재도전 조건

_실험 후 작성._ 판정(채택 / 방식 변경 / 판단 보류), SPEC·온톨로지에 반영한 것, 재도전 조건.

- 결과별로 미리 정해 둔 반영 방향 (실험 전 합의):
  - ①② 통과 → SPEC 갭 분석(AC9, AC11) 확정
  - ① 통과, ② 미달 → 대조 규칙 문제. 색 계열·종류 묶음 규칙을 고치고 재검증, 임베딩 추가 결과가 좋으면 옷 사진 등록을 선택 기능으로 권장
  - ① 미달 → 사진 속 아이템을 사용자가 확인·수정하는 단계를 추가하고, 핏처럼 자주 틀린 속성은 대조에서 제외
  - ③ 미달 → 스키마 검증 실패 시 재요청 1회 규칙 추가 / ④ 미달 → 더 작은 모델 비교, 결과 캐시(AC4)로 체감 지연 완화
- 재도전 조건 후보: 사진 속 아이템과 **어울리는** 다른 옷 추천(조합 품질)은 정답 기준이 없어 이번 범위에서 뺐다. 인터뷰·설문으로 "어울림"의 기준을 확보한 뒤 별도 스파이크로 검증한다.
