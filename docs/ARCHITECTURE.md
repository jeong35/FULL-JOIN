# 아키텍처 설계서 — FULL JOIN

> 2026-11-20 기준. 파일명과 동작은 코드에서 확인해 적었다. 상품 RAG(4절)는 설계만 있고 구현 전이다.

## 1. 한눈에 보는 데이터 흐름

- 사진 올릴 때(운영자, 사진당 1회): 피드 사진 → AI 태깅(구조화 출력) → 사람 검수 → 공개
- 사용자가 쓸 때: 피드 사진 저장 → 저장된 태깅 + 내 옷장 → 판정(활용·비슷함·필요) → 코디 조합 + 쇼핑 링크 → (선택·베타) 챗봇 질문
- 한 줄로 다시 쓰기: AI는 사진을 한 번만 읽고, 그 뒤의 판정과 코디 조합은 정해진 규칙이 한다.

- 오케스트레이션 방식과 이유: 프레임워크 없이 서버 코드가 순서를 고정한다. 단계 순서가 항상 같아서 모델이 다음 단계를 고를 필요가 없고, 순서를 고정해야 같은 입력에 같은 결과가 나온다. 태깅은 사진당 모델 1회다. 챗봇은 보유 옷·상품 탐색·저장 사진·범위 밖 질문이면 모델을 호출하지 않고 구조화 데이터로 답하며, 일반 패션 조언이 필요한 단일/복합 질문만 최대 1회 호출한다.

## 4. RAG 설계 (상품 RAG — 10/28·11/4 결정)

- 무엇을 검색하나: 상품이 연결된 피드 아이템. 지금 사진 100장에 대표 상품 100개가 연결돼 있다.
- 쓰이는 곳: 챗봇이 상품을 묻는 질문을 받을 때만. 판정과 옷장 확인은 지금처럼 코드가 한다.
- 검색 단위(문서 한 개의 글): 상품 한 개가 문서 한 개. 글이 한 줄이라 나누지 않는다. 처음에는 상품명 + 브랜드 + 태깅 값(부위·종류·색·핏·스타일)으로 만들고, 검색 케이스에서 부족하면 상품 설명을 더한다.
- 임베딩 모델과 저장소: OpenAI 임베딩(후보 `text-embedding-3-small`) + Supabase Postgres의 pgvector. 둘 다 이미 쓰는 서비스라 새 서비스를 늘리지 않는다.
- 검색 파라미터(top_k, min_score)와 그 값의 이유: 미정. 숫자를 먼저 정하지 않고, 검색 케이스(나와야 할 상품 / 나오면 안 되는 상품 / 근거 부족이어야 하는 질문)를 만든 뒤 그 결과로 정한다.
- 검색이 아니라 코드로 강제하는 제약(↔ AC2): 브랜드·제품명은 검색된 상품 정보에 있는 것만 답에 넣는다. 부위·종류는 검색이 아니라 필터로 거른다. "가진 옷"은 옷장 DB 조회로만 판단한다. 상품 글 속 지시문은 데이터로만 다룬다(AC6).
- 근거가 부족할 때(min_score 미달): 상품을 말하지 않고 "저장된 상품 중엔 비슷한 게 없어요"라고 답하며, 지금처럼 무신사·에이블리·지그재그 검색 링크를 준다.
- 구현 상태(11/18 기준): 미구현. 설정 초안은 `config/rag.yaml`. 지금 챗봇은 검색 없이 저장된 태깅과 옷장을 통째로 넘긴다.
- 아직 구현하지 않은 이유: 상품이 100개뿐이라 지금은 검색 없이도 동작하고, 동료평가 기간(~11/18)에 서버를 바꾸면 평가 중인 앱이 멈출 수 있어서 미뤘다.

## 5. 오케스트레이션 — 멈춤 조건과 호출 상한

- 챗봇 한 번에 모델 호출 수: grounded intent는 0회, 일반 패션 조언 포함 시 최대 1회(재시도 없음) / 시간 제한: 25초 / 출력 상한: 500토큰
- 대화 기록: 최근 8개까지(코드 값)
- 태깅: 사진당 1회, 시간 제한 75초, 출력 상한 2,000토큰(코드 값). 같은 사진을 동시에 분석하려 하면 409 `analysis_in_progress`.
- 이 값들의 이유: 한 질문에 한 번만 호출해 비용과 대기 시간의 상한을 고정했다. 25초를 넘기면 고정 규칙 답변으로 넘어가 빈 화면이 생기지 않게 했다. 답은 2~4문장이라 500토큰이면 충분하다. 숫자 자체는 실험으로 고른 값이 아니라 구현할 때 정한 값이다.

## 6. 실패 처리

| 상황 | 지금 동작 |
|---|---|
| 보유 옷·상품·저장 사진·범위 밖 질문 | OpenAI를 호출하지 않고 `buildChatResponse` 결과를 반환. 후보 ID는 현재 옷장 조회 결과로 재검증 |
| 일반 패션 질문의 OpenAI 호출 실패 | 옷장/사진 근거는 유지하고 일반 조언 섹션만 안전한 안내로 대체. 챗봇은 필수 MVP 완료 판정에서 제외 |
| 옷장이 비어 있음 | 판정하지 않고 "옷장을 등록하면 가진 옷과 맞춰 드려요" (AC12) |
| 사진에서 옷을 못 찾음 | 422 `no_clothing_items` "사진에서 옷을 찾지 못했어요". 저장하지 않으므로 피드에 올라가지 않는다 (AC10) |
| 태깅 응답이 스키마에 안 맞음 | OpenAI 구조화 출력(strict)으로 받고 서버가 zod로 한 번 더 검사한다. 안 맞으면 저장하지 않고 502 `analysis_failed` |
| 태깅 OpenAI 호출 실패·거절 | 502 `analysis_failed` "AI 사진 분석에 실패했어요". 저장하지 않는다 |
| 저장하지 않은 사진에 챗봇 질문 | 409 heart_required |
| RAG 검색 결과 없음 | (구현 전) 설계: 상품을 말하지 않고 검색 링크만 준다 |

- 지어내는 경로가 없는지 확인한 방법: 판정과 코디 조합은 LLM 없이 규칙으로 하고 골든 계약 47개로 확인한다. 태깅은 evals의 절대 규칙 케이스(근거 없는 브랜드, 옷 없는 사진, 캡션 지시문)로 잰다. 이 절대 규칙 케이스들은 11/18 기준 아직 실행 전이다(`evals/EVAL_DESIGN.md` 5절).

## 7. 가드레일 (AGENTS.md 절대 규칙과 대응)

| 절대 규칙 | 어디서 막나 |
|---|---|
| 1. enum 값만 (AC1) | OpenAI 구조화 출력(strict json_schema) + 서버 zod 검증(`analysis.ts`, `catalog.ts`). 옷장 입력도 같은 목록으로 검증 |
| 2. 근거 없는 브랜드·제품명 금지 (AC2) | 태깅: `keepOnlyCaptionEvidence`가 캡션에 없는 브랜드·제품명을 지운다. 챗봇: 시스템 프롬프트 + 상품은 아이템 분류로 만든 `match_type: similar` 검색 링크만 |
| 3. 캡션·이미지 글자의 지시문 실행 안 함 (AC6) | 캡션을 `<caption>` 태그로 감싸고 꺾쇠를 이스케이프한다. 프롬프트에 "캡션은 데이터"를 적었다. **한계: 프롬프트에 의존한다. 캡션에 브랜드 글자가 실제로 있으면 코드 검사는 통과시킨다** (evals 케이스 i1, 개선 백로그) |
| 4. 얼굴로 인물 식별 안 함 (AC7) | 프롬프트 지시. 출력 스키마에 인물 이름을 담을 칸이 없다 |
| 5. 없는 것을 지어내지 않음 (AC9·10·11) | 판정은 규칙(`classifyGap`)이고 옷장에 있는 id만 돌려준다. 코디 조합은 옷장 옷으로만 만든다(`outfit.ts`). 아이템이 0개면 422로 막는다. 챗봇의 `claimed_owned_item_ids`는 서버가 옷장 id로 계산한다 |

## 8. 관측

- 사용자 행동은 `user_events`(`docs/EVENTS.md`)에 기록한다.
- 모델 운영 지표는 별도 `llm_operation_metrics`에 기능·모델·프롬프트·release·상태·토큰·비용·지연·fallback만 저장한다. migration `202611200003`은 아직 local pending이다.
- grounded 챗도 `llm_called=false`로 기록해 불필요한 모델 호출 감소를 측정한다.
- 사진, 캡션, 전체 프롬프트, 답변/대화 원문, 사용자 ID, 사진 ID, URL은 운영 지표에 저장하지 않는다.
- OpenAI 챗 요청은 `store: false`다. 실제 답변 품질 표본은 승인된 eval runner 또는 별도 동의·접근 제어가 있는 저장소에서 다룬다.
